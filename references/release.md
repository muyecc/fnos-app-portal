# 发布与长期追更

## 每次升级固定输入

记录业务版本、镜像 ID/来源、上游 commit、源码归档 SHA-256、接入版本、FPK 版本和浏览器入口。版本号相同不能代替来源一致。

保留现有功能、环境变量、挂载、网络及用户选择的端口策略。核对上游镜像的功能变体，避免因标签或打包方式变化丢失原有能力。

## 顺序

1. 只读确认生产终态与本地 dirty 状态，不覆盖无关修改。
2. 新目录解压新来源；先看接口/前端变化。
3. 执行目标应用的配置/适配检查；存在 dry-run 或补丁断言时先验证，失败就审查真实差异。本仓库不包含应用专属适配器。
4. 类型检查、针对性前端测试、生产构建。
5. 网关修改需要 Go 测试/vet，Linux 实测 Unix peer 和 WS 回收。
6. 检查产物 manifest；渲染新接入项目并打包。
7. 隔离验证使用独立 project/service 标签，不继承生产标签。
8. 只更新需要变化的业务/接入项目，不整机重启。
9. 查询应用任务终态；验证健康、版本、端口、挂载和资源哈希。
10. 真实客户端复核，然后清理自己的临时资源。

## 静态修复与原生包更新

同一上游 commit 的静态小修复可以设计受控发布：校验归档及来源，先投放哈希资源，再原子替换 index/manifest，保留旧哈希资源供已打开页面使用。此 Skill 不附带某个 NAS 专属的远程热更新工具。

网关二进制、启动配置、应用权限或上游版本发生变化时，走经预检的高版本 FPK 原生更新，不用复制文件冒充包版本升级。

当前工具不支持本地升级时，优先让用户在应用中心更新；需要自动化则先核对当前原生 API。不得导出令牌、改飞牛认证或把卸载重装作为默认方案。

## 端口与运行数据

仅飞牛模式：检查所有旁路，不能只检查业务容器自己没有 ports，而忽略其他转发容器。

保留内网直达模式：保留独立转发项目、固定内网 IP 绑定、动态服务名解析和业务鉴权。升级检查应验证用户保留的实际端口可用，不能仍把关闭该端口作为通过条件。

Docker 重建会丢弃可写层。不要把 /data、/tmp 或浏览器 profile 整体当作可以忽略的临时文件。先检查具体变化和持久化边界，再决定是否重建。备份策略按用户要求，不默认增加全量副本。

## 公开交付边界

公开接入源码和示例配置时，排除生产 plan、OAuth profile/令牌、业务 .env、私有镜像、数据库、上传文件和完整 inspect。不把镜像打包进 Skill。

发布本 Skill 到 GitHub、选择仓库/许可证、提交推送及对外发布均由用户明确决定；生成本地草稿不等于已经授权发布。
